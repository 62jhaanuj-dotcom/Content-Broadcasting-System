================================================================================
CONTENT BROADCAST SYSTEM - ARCHITECTURE NOTES
================================================================================

 PROJECT OVERVIEW
The Content Broadcast System is a backend service that enables teachers to upload
subject-based educational content (images) and allows principals to approve it.
Once approved, content is automatically broadcasted via public APIs with subject-based
rotation scheduling, ensuring content is shown only within teacher-defined time windows.

================================================================================
1 AUTHENTICATION & RBAC FLOW
================================================================================

JWT-Based Authentication:
 Flow:
   1. User signup/login  credentials validated  JWT token generated
   2. Token includes: user_id, role, email  7-day expiry
   3. All protected endpoints require Authorization header: "Bearer <token>"
   4. AuthMiddleware validates token and extracts user info

Role-Based Access Control (RBAC):
 Two roles implemented:
   - TEACHER: Can upload content, view own uploads, access public broadcast API
   - PRINCIPAL: Can view all content, approve/reject, manage workflow

 Authorization Flow:
   1. JWT token decoded  user role extracted
   2. RoleMiddleware checks if user role matches endpoint requirement
   3. If role mismatch  403 Forbidden response
   4. If valid  request proceeds to controller

Files Involved:
- src/middlewares/authMiddleware.js - Token validation
- src/middlewares/roleMiddleware.js - Role checking
- src/services/authService.js - JWT generation + password hashing (bcrypt)

3 SUBJECT-BASED ROTATION LOGIC (CRITICAL)
================================================================================

Problem Statement:
- Multiple teachers upload different content
- Each subject (Maths, Science) has independent rotation
- Content should rotate based on duration
- Must respect time windows (start_time  end_time)
- Students access via public API for active content

Solution Architecture:
 Subject-isolated rotation:
   1. Content is grouped by subject
   2. Each subject maintains independent schedule
   3. Rotation cycle = sum of all durations for that subject
   4. Current position = (current_time_minutes % rotation_cycle)

Example Rotation:

   Maths (Teacher 1):
   - Content A (5 min): 0   5
   - Content B (5 min): 5   10
   - Content C (3 min): 10   13
   Total Cycle: 13 minutes
   
   If current_time = 7 minutes:
   - Cycle position = 7 % 13 = 7
   - Active content = Content B (5 <= 7 < 10)
   - Next rotation in 3 minutes
   
   Science (Teacher 2):
   - Independent rotation (not affected by Maths)

Algorithm Implementation (src/services/schedulingService.js):

```javascript
1. Group teacher content by subject
2. Filter out anything outside its active time window
3. For each subject, load only that subject's schedule rows
4. Calculate total = sum(all durations for that subject)
5. current_position = floor(now_millis / 60000) % total
6. For each schedule (ordered by rotation_order):
   - If current_position < cumulative_duration:
     - Return this content as the active item for that subject
   - Else cumulative_duration += schedule.duration
```

Edge Cases Handled:
 No content available  returns "No content available"
 Content outside time window  filtered out
 No schedule defined  returns "No content available"
 Invalid subject  returns empty (not error)

4 UPLOAD SYSTEM & FILE HANDLING
================================================================================

File Upload Flow:

1. VALIDATION (uploadMiddleware - multer):
    Allowed formats: jpg, png, gif
    Max file size: 10MB
    Required fields: file + title + subject
   
2. STORAGE:
    Method: Local disk storage
    Location: src/uploads/
    Filename format: timestamp + extension
    Accessible via: GET /uploads/{filename}

3. METADATA TRACKING:
    file_path: Full path to uploaded file
    file_type: MIME type (image/jpeg, etc.)
    file_size: File size in bytes
    file_name: Original filename for reference

Middleware Stack for Upload:

```
POST /api/content/upload
  
authMiddleware (verify token) 
  
roleMiddleware("teacher") (verify role) 
  
upload.single("file") (multer validation) 
  
contentController.uploadContent (business logic)
```

Upload Validation:

```javascript
- title: Required, non-empty
- subject: Required, trimmed to lowercase
- file: Required, validated by multer
- startTime/endTime: Optional, validated ISO format
- description: Optional

If startTime/endTime provided:
- Must be valid ISO datetime
- endTime must be AFTER startTime
```

5 CONTENT APPROVAL WORKFLOW
================================================================================

Content Lifecycle: PENDING  APPROVED/REJECTED

State Diagram:

   
      PENDING    (Initial state after upload)
   
          
     
              
 APPROVED   REJECTED
 (goes live) (stores reason)

Approval Workflow:

1. TEACHER UPLOADS:
   - POST /api/content/upload
   - Content created with status = "pending"
   - Only visible to uploader and principal

2. PRINCIPAL REVIEWS:
   - GET /api/approval/pending (view pending content)
   - GET /api/approval/all (view all content)
   - Content shows: title, description, teacher_name, status

3. PRINCIPAL APPROVES:
   - PUT /api/approval/{id}/approve
   - Updates: status  "approved"
   - Sets: approved_by  principal_id
   - Sets: approved_at  current_timestamp
   - Content becomes eligible for broadcast

4. PRINCIPAL REJECTS:
   - PUT /api/approval/{id}/reject (body: { reason })
   - Updates: status  "rejected"
   - Sets: rejection_reason  provided reason
   - Content NOT eligible for broadcast
   - Reason visible to teacher

Audit Trail Maintained:
 approved_by: Which principal approved
 approved_at: When it was approved
 rejection_reason: Why it was rejected (if rejected)
 created_at: When uploaded

6 BROADCASTING & PUBLIC API
================================================================================

Public Endpoints (NO AUTHENTICATION REQUIRED):

1. GET /api/broadcast/live/:teacherId
    Returns one currently active content item for the teacher
    Respects independent rotation per subject
    If multiple subjects are active, one active subject is selected at a time
    Only shows approved + within time window
    Query param: ?subject=maths returns a single subject item

2. GET /api/broadcast/teacher/:teacherId
    Returns the grouped live view by subject
    Shows one active content item plus rotation info per subject

3. GET /api/broadcast/live/:teacherId/:subject
    Subject-specific rotation
    Only shows content for specified subject

Assignment-style aliases:
1. GET /content/live/teacher-1
2. GET /content/live/teacher-1/maths

Response Format:

```json
{
  "message": "Content retrieved successfully",
  "data": {
    "id": 1,
    "title": "Question Paper - Chapter 5",
    "subject": "maths",
    "file_path": "src/uploads/1234567890.jpg",
    "file_type": "image/jpeg",
    "uploaded_by": 2,
    "teacher_name": "Mr. John",
    "status": "approved",
    "start_time": "2026-04-27T10:00:00Z",
    "end_time": "2026-04-27T12:00:00Z",
    "approved_at": "2026-04-26T15:30:00Z"
  },
  "rotationInfo": {
    "totalDuration": 15,
    "currentSlot": 7,
    "contentDuration": 5,
    "rotationOrder": 1,
    "subject": "maths",
    "activeSubjectCount": 2
  }
}
```

Edge Case Handling:

```javascript
// Case 1: No content available on teacher-wide single-content endpoint
Response: { message: "No content available", data: null }

// Case 2: Invalid teacher ID
Response: { message: "No content available", data: null }

// Case 3: Valid teacher, but no approved content
Response: { message: "No content available", data: null }

// Case 4: Approved but outside time window
Response: { message: "No content available", data: null }

// Case 5: Approved but no schedule row on subject-specific endpoint
Response: { message: "No content available", data: null }
```

Caching Considerations (Future Enhancement):
- Current implementation: Calculates rotation dynamically
- Optimization: Cache rotation for 1 minute
- Trade-off: Slight delay vs. reduced DB queries

8 MIDDLEWARE USAGE & ORDER
================================================================================

Middleware Stack Order:

```
App.js

express.json() - Parse JSON bodies
  
Logger middleware - Log all requests
  
Static middleware - Serve uploaded files
  
Routes (each route has its own middleware stack)
  
404 handler - Catch undefined routes
  
errorMiddleware - Final error handler (MUST BE LAST)
```

Protected Route Example:

```
POST /api/content/upload
  
authMiddleware  Validates JWT token
  
roleMiddleware("teacher")  Checks if user role = teacher
  
upload.single("file")  Validates file upload
  
contentController.uploadContent  Business logic
```

Custom Middlewares:

1. authMiddleware:
   - Extracts JWT from Authorization header
   - Verifies signature
   - Sets req.user = { id, role, email }
   - Returns 401 if invalid

2. roleMiddleware(role):
   - Checks if req.user.role matches required role
   - Returns 403 if mismatch
   - Supports: "teacher", "principal"

3. uploadMiddleware (multer):
   - Validates file format: jpg, png, gif
   - Enforces max size: 10MB
   - Stores to: src/uploads/
   - Adds req.file with: path, filename, size, mimetype

4. errorMiddleware:
   - Catches all thrown errors
   - Returns structured error response
   - Logs errors for debugging
   - Maps specific errors to appropriate HTTP status codes

- 401: Unauthorized (missing/invalid token)
- 403: Forbidden (insufficient permissions)
- 404: Not Found (resource doesn't exist)
- 409: Conflict (duplicate email on signup)
- 500: Internal Server Error

Error Response Format:

```json
{
  "message": "Descriptive error message",
  "status": "error",
  "code": "ERROR_CODE"

```

- INVALID_AUTH - Wrong password
- FORBIDDEN - Access denied
- NOT_FOUND - Content/user not found
- BAD_REQUEST - Validation failed
- INVALID_FILE_TYPE - Wrong file format

================================================================================
 SECURITY MEASURES
================================================================================

Authentication:
 Password hashing: bcrypt with 10 salt rounds
 JWT tokens: Signed with JWT_SECRET (7-day expiry)
 Token validation: On every protected route

Authorization:
 Role-based access: RoleMiddleware enforces
 Resource ownership: Teachers can only see their own content

Data Validation:
 Input validation: All endpoints validate input
 File validation: Type and size checked by multer
 Email format: Regex validation

Sensitive Data Protection:
 Password: Never returned in responses
 Rejection reason: Only visible to teacher + principal
 Approved by: Only visible to admin

SQL Injection Prevention:
 Parameterized queries: All DB queries use $1, $2 placeholders
 No string concatenation in SQL

CORS Configuration:
 Allow all origins (for public API)
 Can be restricted to specific domains in production

12 ASSUMPTIONS & DESIGN DECISIONS
================================================================================

1.  File Storage: Local disk (not S3)
   Reason: Simplicity for MVP, easy to migrate later

2.  Rotation by Time: Global time-based (not per-session)
   Reason: Consistent experience across users, fair rotation

3.  Approval Required: All content must be approved
   Reason: Content quality control, security

4.  Time Zone: UTC (ISO format dates)
   Reason: Consistent across regions, no ambiguity

5.  Subject Isolation: Independent rotations per subject
   Reason: Teacher controls subject separately

6.  No Content Versioning: Replace on reupload
   Reason: Simplicity, can add later if needed

7.  JWT over Sessions: Stateless authentication
   Reason: Scalable, no session storage needed

8.  Soft Delete: Not implemented (hard delete)
   Reason: Can add audit trail later if needed
